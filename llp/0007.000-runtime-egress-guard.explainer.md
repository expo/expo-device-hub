# LLP 0007.000: Simulator egress guard

**Type:** Explainer
**Status:** Active
**Systems:** ServeSim
**Author:** Gabe Debes
**Date:** 2026-10-26
**Revised:** 2026-10-30
**Related:** LLP 0007, LLP 0011, LLP 0003

## Purpose

Serve-sim keeps an egress guard loaded from Simulator boot and changes its policy
without rebooting. It uses the existing capability loader, per-device launch
state, device lock and authenticated session controls. EAS warm-session transport
and job handoff are downstream callers, not a second guard owner
[confirmed: Gabe Debes, 2026-10-26–30, resident guard direction and consolidation].

## New outbound attempts

Enable blocks remote destinations supplied to `connect`, `connectx`, addressed
`sendto` and `sendmsg`, including implemented NOCANCEL entries. Disable passes
those calls through. Existing connected sockets, destination-less sends, file
writes, queued traffic and operations already in flight are left alone. An
addressed TCP send can use its existing peer regardless of its supplied address.
Enabling is not an instant network cutoff and does not require draining old
connections [confirmed: Gabe Debes, 2026-10-29, accepted new-attempt boundary].

Loopback and permitted local destinations remain available. Host worker processes,
serve-sim and transport tunnels are outside the Simulator guard; Android has a
separate fence. Raw syscalls and late-loaded competing interposers are outside
this interposition contract [observed: native interpose table and classifier].

## Enrollment and policy

Enrollment is separate from enabled policy. The pinned loader, guard, policy
page, startup discovery record and ownership metadata survive disable and ordinary
session release so later helpers find the same page. Generic config publication
cannot withdraw a resident record. Surviving config or insert evidence without
valid launch metadata rejects publication and cleanup before mutation
[observed: capability config and launch manager].

The loader has a startup-only `allProcesses` scope and a separate
`serve_sim_startup_all_processes` entry point for libSystem-only resident images.
It reuses the startup config parser and matches the actual callback image.
Deferred app capabilities keep their existing scope. An older loader cannot
silently downgrade the resident guard to app-only initialization
[observed: loader C, startup header and config writer].

Resident records are parsed at the disk boundary with field/path errors. Native
probe results use the same boot-identity schema. Malformed resident records reject
rather than disappearing during a generic read-modify-write. Boot enrollment has
no session owner; live session records authorize policy mutations
[observed: resident state parser and ownership checks].

## Startup and adoption

`--enable egressGuard` selects block; `--disable egressGuard` selects pass-through.
The initial choice supplies the immutable warmup policy. Both flags together
reject. A resident boot requires an explicit choice on startup and adoption;
there is no silent warmup default. Uninstrumented sessions without a request
retain their existing path [confirmed: Gabe Debes, 2026-10-26, startup and adoption
controls; observed: override parsing].

Initial enrollment requires one stopped, exact Simulator UDID. Preparation pins
private assets and publishes discovery before strict boot. Binding records the
native `launchd_sim` PID and start time. Preparation, boot and policy admission
share the device lock. A replacement boot, foreign boot or boot-capable readiness
wait cannot reuse the old enrollment [observed: resident startup transaction].

Private adoption checks compatibility before consuming its one-shot claim, then
revalidates under the device lock. Policy publication and native self-check
precede capture/video configuration and success. Failure after consumption leaves
the claim consumed; original and cleanup errors remain available. Adoption cannot
retire another resident device or inherit the server's warmup policy as a job
default [observed: private owner and egress adoption paths].

## Policy acknowledgement

The guard maps its page through the immutable startup record. The controller
changes mode and generation on the same inode. Missing or malformed policy blocks
covered new remote attempts. A fresh Simulator helper verifies the pinned guard
image, mapped page identity, mode and generation. Publication validates assets and
boot before mutation and revalidates after the helper. Failure rejects readiness
or configuration and attempts blocking cleanup [observed: guard, controller,
self-check and policy publication].

This acknowledges the checked process and policy, not observation by every
process or an in-flight drain. Process coverage, proxy readiness, final-source
performance and integrated device behavior require their own validation.
Measurements, commands and review status belong in the PR, outside this design
contract [observed: self-check boundary; confirmed: Gabe Debes, 2026-10-30,
consolidate into one stable LLP].

## Right panel controls

The Tools panel offers “Block new external connections” and explains that existing
connections stay open. Unenrolled devices have unavailable controls. Authenticated
`egress.status` and `egress.set` actions use the existing exact-device policy,
session ownership and device lock. They cannot enroll, boot, claim or configure
capture/video. Mutations acknowledge only after the native self-check
[observed: action schemas, policy functions and selected-device restrictions].

The client reads on mount and after every update, including failure because
blocking cleanup can change policy. Failed reads disable mutation and offer an
explicit retry. Device-keyed components ignore replies after unmount. There is
no periodic polling [observed: egress Tools-panel component].

## Native argument handling

Caller structures are inspected through bounded `vm_read_overwrite` copies.
Unreadable arguments return `EFAULT`. Accepted short mapped-IPv6 addresses are
zero-filled before classification. `connectx` does not exempt UDP `AF_UNSPEC` as a
disconnect because that operation can send its iovec. These rules preserve the
covered syscall behavior without peer lookups or an fd cache
[observed: guard and destination classifier].

## Resident boot reclamation

Disable and release retain live boot assets. Camera commands that replace an
app's insert list, Simulator reboot, and direct/grid shutdown refuse resident
enrollment before changes. Loader-based camera controls do not require that
insert replacement; their integration must preserve resident discovery
[observed: resident operation guards; camera integration remains separate].

Reclamation requires recorded PID absence, a hash-pinned probe reporting no boot,
the exact device in Shutdown, then another absent boot/PID check. Pending boots,
unknown visibility, permission failures, foreign owners and replacement boots
retain enrollment. Validate directory ownership, named files, hashes and page
identity before mutation. Metadata failure restores config/inserts/state;
confirmed reclamation unlinks named assets without recursive deletion. Preboot
rollback can remove only new unmapped owned assets. Uncertain postboot cleanup
cannot unlink or replace a live mapping [observed: reclamation and rollback].
