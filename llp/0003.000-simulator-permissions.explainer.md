# LLP 0003.000: Simulator permissions

## Scope

This document explains the implemented iOS Simulator permission controls shared by
the serve-sim CLI, standalone preview and Device Hub. The public host-action
contract remains in [LLP 0003](0003-serve-sim-http-api.spec.md#app-permissions).
Hub control integration remains in
[LLP 0013](0013-hub-client-input-and-control.explainer.md#app-permissions).
Android uses a separate backend; the shared browser hook does not make the iOS
native mechanisms apply to Android. [observed: serve-sim `src/permissions.ts`;
`packages/@expo/hub-client/src/useIosDevice.ts`,
`packages/@expo/hub-client/src/useAndroidDevice.ts`]

Paths beginning with `src/` or `Sources/` below are relative to
`packages/serve-sim/packages/serve-sim`. Other paths are relative to the repository
root. This draft records implementation and observed limits; it does not claim
human approval or compatibility with every Simulator runtime.

## Permission contract

`grant`, `revoke` and `reset` are different operations. Revoke denies access;
reset restores an undetermined state so an app can request authorization again.
`reset all` applies the catalog sequentially and can fail after earlier services
have changed. It is not a transaction. [observed: `src/permissions.ts`, `applyOne`
and `permissions`]

The CLI accepts a device UDID or name and a bundle ID. Host actions retain
`permissions.set {udid, action, service, bundleId}`, `permissions.list` and
`permissions.resetAll`. App-scoped lists retain the legacy `tcc`, `location` and
`notifications` fields and add normalized rows with an ID, label and one of
`granted`, `denied`, `limited` or `undetermined`. A command ACK is not a replacement
for that list. [observed: `src/permissions.ts`, `permissionStates`;
`src/host-actions.ts`]

CLI `--value` supports Photos limited access, notification critical authorization
and location modes. The current host-action/UI set contract does not carry a
`value`, so those extra CLI options are not all exposed by Hub controls.
Notification rows summarize authorization: provisional or ephemeral authorization
with `allowsNotifications` also maps to granted. That label does not describe
every presentation setting or prove delivery. [observed: `src/permissions.ts`;
`src/host-actions.ts`; `packages/@expo/hub-client/src/ios-permissions.ts`]

## Native services

There is no single notification API that controls every permission family.
Notification state belongs to BulletinBoard, privacy permissions to tccd, and
location to locationd. Editing a backing store alone does not establish that its
running service or the app has adopted the change. The implementation uses service
writes and family-specific reads. Numeric codes are service-specific; only the
normalized row states are shared. [observed: `src/permissions.ts`;
`Sources/SimPermissions/sim-permissions.m`]

### Notifications

`serve-sim-permissions` runs inside the selected Simulator through `simctl spawn`.
It loads BulletinBoard and uses `BBSettingsGateway` to read and write section
information. It does not edit `VersionedSectionInfo.plist`. A grant sets authorized
status 2, denial sets 1, and reset sets 0 while retaining an existing section.
Reset of an absent section is a no-op. Grant can create a section before the app
is installed. [observed: `Sources/SimPermissions/sim-permissions.m`, `notifications`]

Required selectors are checked before publishing a change. Setting
`allowsNotifications` also affects authorization, so the explicit authorization
status is written last; otherwise reset can become denial. The helper polls
gateway readback for authorization, allowed state and the critical flag before
reporting success. Grants also set and confirm enabled lock-screen and Notification
Center settings (2). Missing APIs, exceptions and unconfirmed writes fail rather
than producing a success ACK. These are private Simulator APIs, checked at runtime;
availability is not a promise for untested runtimes. [observed:
`Sources/SimPermissions/sim-permissions.m`]

Using the numeric setters alone avoids overlapping legacy alias writes whose
dictionary order could otherwise change the result. [inferred]

### TCC privacy permissions

Camera, microphone, Photos, Contacts, calendar, reminders and the other cataloged
TCC services use `TCCAccessSetForBundleIdWithOptions` or
`TCCAccessResetForBundleIdWithOptions`. The helper requires `kTCCSetNoKill`, passes
the no-kill option and checks the daemon's Boolean result. Failure or missing
symbols is an error. A daemon-accepted change does not guarantee that every app
framework invalidates its cached authorization immediately. [observed:
`Sources/SimPermissions/sim-permissions.m`, `tcc`]

Reads use read-only SQLite against TCC.db. The cross-app TCC information API
reported full and limited Photos access alike as granted in the native probe;
the database preserves the distinction. Value 0 maps to denied, 2 to granted, 3
to limited, and a missing row to undetermined. The sqlite process allows 4.5 seconds
for transient writer locks inside its five-second deadline. It never writes the
database. [observed: `src/permissions.ts`, `readPermissionDatabase`, `readTcc` and
`permissionStates`; native TCC probe, 2026-10-23;
`src/__tests__/permissions-sqlite.test.ts`]

### Location

Location writes use `simctl privacy`. The CLI waits for locationd's persisted
`Authorization` value: reset 0, denied 1, in-use 2 or always 4. These are locationd
store values, not public `CLAuthorizationStatus` enum values. The helper reads
locationd's correctly keyed app entry without modifying it. A cross-app
CoreLocation getter returned 0 while the app's public API reported always
authorization in the iOS 27.1 probe, so it is not used for status. A missing
installed-app entry can prevent confirmation even when simctl returned success.
[observed: `src/permissions.ts`, `readLocation` and `setLocation`;
`Sources/SimPermissions/sim-permissions.m`; native location probe, 2026-10-23]

## Ordered requests and authoritative browser state

Within one host process, permission reads and writes are serialized by
canonical Simulator UDID and bundle ID. Admission preserves arrival order while
resolving device names, so a later UUID read cannot overtake an earlier name-based
reset. Different apps have separate execution queues; a device-wide list waits
for all earlier app work, and later app work waits for that list. Unscoped lists
can resolve shutdown device names because they read persisted TCC state. Alias
resolution prefers a unique booted match and rejects ambiguous names. Separate
middleware mounts share these queues because they access the same host's native
Simulator state. Closing a socket does not
cancel the host's running native action; a reconnect read queues behind it. This
queue is in memory and is not a cross-process lock for independent CLI invocations
or a transaction that survives a host-server restart. [observed:
`src/host-actions.ts`, `permissionAdmission` and `permissionRequests`]

The Hub adapter lists after a write or reset. It validates normalized rows instead
of manufacturing a granted state from an ACK. The Permissions section refreshes
state every five seconds and on focus only while expanded, on both platforms;
the iOS hook also refreshes
when the shared control socket reconnects. Its target identity includes the
host URL, Simulator UDID and app, so equal UDIDs on different hosts do not share
pending ownership. Backend replacement invalidates retired reads and cached rows
while preserving unresolved writes for that target. [observed:
`packages/@expo/hub-client/src/ios-permissions.ts`,
`packages/@expo/hub-client/src/useIosDevice.ts` and
`packages/@expo/hub-client/src/useAppPermissions.ts`]

Generation and per-permission version checks reject retired or overlapping
responses. Reads remember which writes were pending when they began. If a write
loses its reply, Hub keeps its controls pending until a later successful ordered
read establishes the outcome; failed recovery does not release that ownership.
Mutation errors remain visible across successful background reads. The section
offers Retry on errors even when rows remain visible and writes are held, so
recovery does not depend on polling or releasing ownership prematurely. [observed:
`packages/@expo/hub-client/src/useAppPermissions.ts`,
`packages/@expo/hub-client/src/app-permissions.ts`;
`packages/@expo/hub-client/src/__tests__/use-app-permissions.test.tsx`;
`packages/@expo/hub-components/src/dashboard/PermissionsSection.tsx` and
`packages/@expo/hub-components/src/__tests__/permissions-section.test.tsx`]

The standalone preview also reads after mutations, on opening its panel, focus
and periodic refresh. It rejects old generations, coalesces reads per target and
keeps mutation errors separate from refresh errors. Location Always has its own
selection: in-use is not always, while absent or zero authorization selects Reset.
Its pending implementation is separate from the Hub hook. [observed:
`src/client/components/app-permissions-tool.tsx`;
`src/__tests__/fixtures/permissions-ui.child.ts`]

## Persistence boundaries

Permission status is service state, not a browser preference. These boundaries
must not be grouped into one persistence claim:

- Page reload and control reconnection discard or refresh browser state and list
  current service values. Deferred-response tests cover stale replies and lost
  write replies. [observed: the two browser implementations and their tests above]
- The native helper is invoked per command. A new helper or serve-sim process reads
  service state again instead of restoring a process-local permission mirror.
  [observed: `src/permissions.ts`]
- App relaunch and Simulator reboot restart different processes. Persistence must
  be checked separately for each permission family and runtime, including the
  app's public state and delivery where applicable. A notification persistence
  result does not establish persistence for TCC or location. [confirmed: Gabe
  Debes, 2026-10-23]
- Persisted authorization and an app's cached public-framework result can differ.
  Camera and microphone reflected live changes in the tested apps. Contacts and
  Photos add-only retained cached values; full-to-limited Photos and a retained
  EventKit store needed explicit app relaunch in the iOS 26.5 fixture. Tests name
  that boundary rather than calling those public results live. [observed:
  `src/__tests__/permissions.e2e.test.ts`; native TCC probe, 2026-10-23;
  [local permission validation][permission-validation]]

### Fresh notification initialization boundary

A grant confirms authorization, not notification delivery readiness. On iOS 27.1,
a never-requested app reported `UNAuthorizationStatusAuthorized` after a service
grant, but local scheduling failed with "Source is not authorized." Waiting and
app relaunch did not fix it. Its normal `requestAuthorization` then returned true
without prompting, and local delivery worked without a restart.
[observed: native notification experiments, 2026-10-23; recorded limits
in [local permission validation][permission-validation]]

No service-only initialization fix has been validated. Setting `pushSettings` to
63 did not fix the scheduling failure. That negative result must not be treated
as a working recipe or copied into production. A fresh app may still need its
normal authorization request. This is an unresolved support boundary, not proof
that external initialization is impossible. [observed: native notification
experiments, 2026-10-23; [local permission validation][permission-validation]]

The fresh pre-grant regression intentionally makes the normal app request before
checking enabled alerts and local delivery. It proves pre-grant followed by normal
app initialization, not grant-only delivery. Remote APNs and critical notification
delivery were not tested; critical authorization flag readback is a narrower
check. [observed: `src/__tests__/permissions.e2e.test.ts`;
[local permission validation][permission-validation]]

## Helper, fixture and packaging

`Sources/SimPermissions` is the production service helper. Its build embeds scoped
TCC and BulletinBoard entitlements in the Mach-O `__TEXT,__entitlements` section
and signs ad hoc without private code-signing entitlements. Putting the private
entitlement in the signing blob was rejected by Simulator spawn policy in the
initial experiment. The helper does not inject code or restart the target app or
SpringBoard. [observed: `Sources/SimPermissions/build.sh`, `entitlements.plist`;
native notification experiment, 2026-10-23]

`Sources/SimPermissionsFixture` is a separate test/sample app. It makes normal
public-framework requests, exposes buttons and writes public state, heartbeat,
PID, launch count and local-delivery telemetry. This independently checks what
the app observes. It is built by `Sources/build-test-fixtures.sh`, not the
production helper build. [observed: `Sources/SimPermissionsFixture`;
`src/__tests__/permissions.e2e.test.ts`]

The arm64 helper ships as `dist/simperm/serve-sim-permissions`; its build sources
and the fixture app are excluded from the npm files list. A missing helper reports
an error rather than compiling a replacement at runtime. Hub vendors the packed serve-sim package, so it
receives the production helper without the test app. The CLI entry and Node module scope follow [LLP 0003](0003-serve-sim-http-api.spec.md#cli-entry-selection). Helper lookup supports source,
bundled and compiled CLI layouts; mounted host actions resolve the packaged CLI
rather than executing the host application's entry point. [observed: serve-sim
`package.json`, `build.ts`, `src/permissions.ts`, `src/middleware.ts`;
`packages/expo-device-hub/scripts/vendor.ts`, `package.json`]

The sample records notification delegate events on the main thread, alongside
its UI and timer snapshots. Its plist includes both legacy and full-access
EventKit usage descriptions so the pre-iOS 17 request branches have the required
keys. [observed: `Sources/SimPermissionsFixture/permission-fixture.m`, `Info.plist`]

## Coverage boundaries

The durable regressions cover notification grant/denial/reset, absent-section
reset, repeat calls, fresh pre-grant initialization, TCC and location public state,
explicit relaunch boundaries, reset-all heartbeat, native errors and compiled
dispatch. SQLite lock tests use a private database. UI tests exercise deferred
responses, target changes, backend replacement, host identity and failed recovery.
They do not substitute for device-backed delivery tests. [observed:
`src/__tests__/permissions*.test.ts`, `compiled-permissions.e2e.test.ts`,
`host-actions.test.ts`; `packages/@expo/hub-client/src/__tests__/use-app-permissions.test.tsx`]

An EAS CLI acceptance check must exercise `simulator:control` through the real
serve-sim control channel; helper-only or direct CLI tests do not cover that path.
Local discovery adapters do not establish hosted session discovery, and local
notification delivery does not establish remote APNs delivery. [confirmed: Gabe
Debes, 2026-10-23]

Validation results, run-specific commands and CI links belong in the PR, not this
design document. [observed: `packages/serve-sim/REVIEW.md`]

The open limits are fresh notification initialization, app-framework caching,
untested runtime/API combinations, unaudited public behavior for some cataloged
TCC families, and hosted/APNs delivery. A successful service read must not be
presented as proof that all of these boundaries work. [observed: tests and
experiment limits cited above]
